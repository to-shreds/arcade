# Arcade expansion: Work implementation specification

Prepared 2026-11-27. This is the governing project brief for a new ChatGPT Work implementation session. It is a plan, not an assertion that any new features exist. Use the highest appropriate thinking effort available. Work on the actual repository and deliver working, tested software and actual educational content, not a proposal, sample-only app, or script that the owner must run to populate it.

## 1. Mission and decisions

Extend the existing Family Arcade with (1) an exceptionally comprehensive offline children's encyclopedia, (2) an integrated and independently accessible children's dictionary, (3) a simple Windows desktop wrapper with password-protected child mode, and (4) mouse support across all activities, including a Mouse Lab. The encyclopedia and dictionary must be ordinary Arcade HTML activities available in the web and existing Android versions as well as Windows. Maintain one shared web codebase, not divergent forks.

The intended reader is 8–9 years old. Use age-appropriate content and vocabulary, not artificially narrow intellectual subject matter. The child can browse freely within the approved library, ask questions in a search field, follow curated questions, look up words, listen, and play. No live chatbot, live generative answers, API keys, paid API calls, subscription, external search, or requirement for the owner to generate content. ChatGPT Work itself produces the actual content and commits it; offline use is free of API charges. Do not require the owner's API credits.

The user explicitly wants a simple Windows wrapper with a visible Exit button requiring a password; no secret key combination, no risky lockout, and no unrestricted browser. Mouse interaction should be as natural as touchscreen interaction. The owner wants a very comprehensive collection, not a token demo.

Defaults to use unless the owner changes them: plain names Encyclopedia and Dictionary; US English; age 8–9 main explanations with optional deeper material; factual non-graphic treatment of sensitive educational topics; illustrations where they add learning value; text and core images available offline; local-only bookmarks, history and vocabulary list; simple password-protected allowlist for child mode; Windows 11 x64 first, verify runtime requirements and Windows 10/ARM64 feasibility before claiming support. These defaults were proposed, not explicitly individually approved. Ask only about a materially blocking decision; continue on reasonable safe defaults. No password or personal information in GitHub, test fixtures, logs, screenshots or public artifacts.

## 3. Encyclopedia user experience

Add a catalog entry (proposed encyclopedia/) with game.json, icon, responsive HTML/CSS/JS, standard Home behavior and shared styles. No multiplayer adapter needed. The homepage has a prominent query field, categories, surprise/random article, fact of the day, favorites, recently viewed topics and a dictionary shortcut. Allow browsing without typing. Search accepts ordinary questions, partial words, misspellings, synonyms and common child phrasing; ranked results have simple titles and short previews, suggestions and disambiguation. No-answer behavior must honestly say the library does not yet have an answer, offer relevant categories and optionally save the query locally for later editorial review. No invented answer, external redirect or forced unrelated match. Use offline deterministic lexical search (normalized tokens, aliases, stems, fuzzy matching, question variants); optional offline semantic search only if it is genuinely useful, compact, tested and has no service dependency. Do not mislabel keyword search as semantic AI.

An article should have a clear title/question, immediately useful short answer (usually 60–150 words), optional deeper explanation in short sections, key facts, relevant visual/diagram, read-aloud, bookmark and 3–8 meaningful follow-up questions with internal links. More detail is optional, not a wall of text. Use real scientific terminology with immediate explanation; distinguish approximate measurements, time-sensitive facts, theories, beliefs, and disagreement from established facts. Prefer concrete examples and familiar comparisons, avoid baby talk. Aim roughly grades 3–4 for main text; readability scores are diagnostics rather than guarantees. Use accessible font sizes, clear focus states, selectable text, well-spaced mouse/touch targets, scroll, Back/Forward and restoration of scroll/search state. Use local history, favorites and saved words with clear/reset controls; no analytics or child identity. Narration should reuse arcade-speech.js and respect Stop, navigation and available local voices; do not promise offline speech if device voice support is absent.

Include optional simple quizzes with explanations, related topics, interactive maps/timelines/size comparisons/labeled diagrams where justified. Avoid gamifying reading with intrusive rewards, ads, timers or mandatory quizzes. Add meaningful illustrations progressively: properly licensed or original accurate static assets, alt text, captions, license and provenance. No remote hotlinks or live image search in child mode, no decorative AI images substituting for facts. Text must work even if an optional visual pack is missing. Use browser-native HTML/SVG/Canvas for reusable educational diagrams. Verify geographic and quantitative scales and explicitly mark approximations.

## 4. Comprehensive content scope and editorial inventory

Design a genuinely broad reference collection with a master inventory and priority tiers. Build a pilot of 100–250 representative articles/terms, then a useful internal milestone of approximately 1,000 articles/5,000 words, then expand to at least the order of 5,000 articles and 15,000 headwords, with a comprehensive target of 10,000+ distinct articles, 25,000+ dictionary headwords and around 50,000 meaningful follow-up links/questions. These are planning targets, not artificial caps or a reason to inflate counts. Aim for comprehensive coverage as reasonably achievable, not tens of thousands of shallow near-duplicates. Do not declare full scope complete at pilot or early milestone. If sessions or tools limit completion, commit validated increments and enumerate precise remaining inventory, counts and next batch; no claims of background work or time promises. Treat count targets as provisional until a real coverage map justifies them; explain any shortfall and ask before redefining a completed comprehensive release.

Include astronomy/space exploration; animals (species, ecosystems and behavior); dinosaurs, fossils and evolution; plants, fungi, microbes; oceans; geology, minerals, climate, weather, water cycle; physics, light, sound, forces, electricity and magnetism; chemistry, elements, materials; human anatomy, senses, genetics, health, hygiene, nutrition; math, patterns and logic; computing, coding, internet, digital safety, AI; engineering, robots, circuits, machines; vehicles, trains, aircraft, ships, infrastructure; countries, continents, landmarks, maps, cultures and languages; ancient civilizations, world history and US history; government, law, society, money and trade; linguistics, writing systems, word origins; art, music, architecture, literature; sports, games, foods and agriculture; inventions, occupations, everyday mechanisms, conservation and surprising everyday questions. Organize at least 30 meaningful subject areas or equivalent taxonomy. Make sure broad categories include specific exemplars (all planets, many individual animals, country profiles, named historical eras, common machines, major body systems, etc.), not only generic overviews. Include cross-category paths such as steam trains → boiling → molecules → atoms → energy.

Each inventory row should identify stable ID, canonical title, aliases/questions, taxonomy, priority, prerequisites/related IDs, source anchors, revision status and review status. Generate actual authored content in batches in Work (not an API generation pipeline), using reliable openly licensed/public-domain structured data where helpful. A generator may deterministically transform licensed facts into meaningful child-friendly prose, but no mechanically inflated entries, placeholders, duplicate paraphrases or counts of empty stubs. Avoid using an entire third-party encyclopedia or proprietary dictionary without permission. Record per-source license, attribution, source URL, retrieval date where material, and claims covered. Prefer authoritative sources (e.g., NASA, NOAA, USGS, Smithsonian, NIH, national libraries, museums, university resources, statistical agencies) appropriate to the topic; verify the actual relevant source, do not invent URLs or infer a citation from a domain. Distinguish public-domain facts from copyrighted expression and images; check all reuse licenses and applicable attribution. For current facts, use dated snapshots or evergreen framing. Never claim that every entry is manually verified when it is not.

Follow-up questions are separate curated graph edges with natural questions linking to real answers. Several phrasings may lead to the same article. Count distinct articles, distinct curated questions/edges and distinct headwords separately; distinguish senses and inflections from unique headwords. Avoid dangling, self-referential or misleading links, link farm padding and circular explanations. Expand missing topics identified by questions and search failures. Keep status counts generated from checked-in records, not claimed manually.

## 5. Integrated children's dictionary

Add a separate catalog activity (proposed dictionary/) and one reusable definition component integrated into Encyclopedia. Reuse the same lexicon and indices, not two copies. Standalone search, autocomplete, A–Z browsing, misspelling suggestions, inflected forms and phrase lookup. In Encyclopedia, mark selected teachable technical terms unobtrusively and allow selection/click of other words (provide explicit Define selected word, touch equivalent, and a keyboard-accessible path). Open a definition panel without navigating away or losing scroll position; users can follow definitions of unfamiliar words and return. Do not make every word a disruptive hyperlink. Consider future integrations in Adventure, Mad Libs, Spelling and other activities after core is stable.

Each headword supports normalized spelling, pronunciation (simple stress guide and optional IPA only if accurate), part of speech, common age-appropriate senses in likely order, plain-language definition, example sentence, inflected variants, irregular forms, useful synonyms/antonyms, and optional etymology when reliable and interesting. Include common idioms, homophones, prefixes/suffixes and technical terms; avoid unnecessary specialized or adult senses. Definitions should not be circular, harder than the word itself, or tautological. Give a concrete example and let the reader explore constituent words. Pronunciation audio uses local speech where available; no API. Personal word collection and review quiz remain local.

Investigate licensed lexical inventories (Princeton WordNet is a candidate, not a mandated dataset), word-frequency lists and openly licensed sources. Verify actual license terms, preserve required notices and attribution, use original child-facing definitions rather than copying a proprietary dictionary. Ensure every meaningful advanced word introduced by the encyclopedia can be looked up, with automated coverage checks and explicit exceptions for proper names and ordinary inflections. Exclude or defer adult-only meanings rather than relying solely on a raw dictionary's filter list. Unknown words get an honest no-match response, suggestions and no external lookup.

## 6. Editorial safety and review

Treat the content as a children's reference product, not unrestricted model output. Prewritten library only, no live prompts, analytics, web search, live dictionary lookups or remote moderation dependency. Content may accurately discuss anatomy, puberty/reproduction at basic biological level, evolution, health, illness, death, religion, history, politics, war and other complex subjects in factual, age-appropriate, non-graphic terms. Do not present beliefs as fact, political advocacy, discriminatory stereotypes, explicit sexual material, graphic violence, glorification, instructions for harmful acts/weapons, self-harm instructions, substance misuse instructions or individualized medical/legal advice. For unsafe or particularly sensitive questions, provide a short neutral response such as “That's a question to talk about with a parent or trusted grown-up.” Do not block harmless educational questions simply because they mention a sensitive word; use context and curated search routes. Safety-oriented questions may receive simple protective advice appropriate for a child. No collection or transmission of personal questions. Allow parents to restrict specific categories in Windows mode if practical without complex setup.

Editorial pipeline: inventory → source evidence → original draft → independent review for claim fidelity, reading level, coherence and safety → correction → schema/graph/search/license checks → publish only approved items. Maintain machine-readable review status, provenance and issue log. Automated lint checks catch schema, broken links, missing words, duplicates, dangerous terms/context flags, unrealistic numbers, reading complexity, coverage gaps and inconsistent claims, but never substitute for substantive review. Sample across every domain, test challenging searches and sensitive examples, review all flagged entries before publication; record what was actually checked and any unresolved editorial gaps. Build regression fixtures including innocent queries with ambiguous terms (e.g., bat, charge, cell), misspellings, unsafe prompts, false premises and requests outside coverage. Do not count unreviewed drafts as approved. Use an adult-only source manifest; citations must not provide a route to the public web in locked mode.

## 7. Data architecture, performance and offline packaging

Use durable stable IDs and a versioned content schema (JSON/JSONL or similarly inspectable structured files). Store topic shards and dictionary shards by category/ID range or prefix, compact prebuilt search index, graph and manifests; lazy-load rather than loading tens of thousands of entries or images at startup. Use deterministic tooling to validate, rebuild indices and count content. Separate editorial source records/metadata from optimized child runtime packs; keep everything reproducible from source. Avoid placing generated duplicate corpora, build caches or giant unnecessary assets in Git. Measure text and image pack sizes, startup, search responsiveness, memory, caching and update behavior on low-end mobile as well as desktop. Targets to benchmark: search results within about 300 ms warm on desktop, usable mobile interactions, no main-thread stalls or fetching entire image collection; report measured conditions, not unsupported guarantees.

Integrate with existing Arcade offline-manifest generator and atomic updates; determine whether core text/indices should be included in full offline package and whether large optional image packs need separate verified manifests. Baseline complete text and dictionary must remain available after a successful offline install and update, including cross-links, search and quizzes. Test actual network disconnected; verify corrupted/incomplete update preserves prior working version and data. Use local storage or IndexedDB for personal progress with namespaced, versioned keys and migrations, no existing save loss. Ensure hosting, storage quotas, Github file limits and Android package constraints are respected. Ordinary hosted Arcade and Android get the same content without requiring new Android APK if existing bridge sufficient; test before claiming. Avoid new paid backend, runtime model, secrets, remote fonts, CDN dependencies or browsing in encyclopedia/dictionary.

## 8. Native Windows wrapper: simple, recoverable and restricted

Build a Windows desktop executable (proposed windows-wrapper/, C#/.NET with Microsoft WebView2, verify supported versions and official SDK behavior). Prefer a packaged trusted local Arcade snapshot using WebView2 virtual-host mapping or equivalent secure local origin, so offline use works and arbitrary remote HTML cannot modify the security policy. Parent-approved update mechanism reuses verified Arcade snapshots; preserve atomic last-known-good and existing saves. Hash verification alone does not authenticate a malicious manifest; fetch updates through trusted official repo/release HTTPS, validate origin/version/manifest and implement appropriate integrity/authenticity controls. No automatic use of arbitrary remote scripts or child-provided paths. Keep standalone EXE or small self-contained install package as simple as possible; explain WebView2 Runtime dependency and actual target architecture, offline first launch, installation/update, SmartScreen/unsigned status and fallback if runtime missing. Do not promise one EXE if actual dependencies require packaging. Never use admin privileges or permanent system changes for ordinary accidental-exit protection.

First run: parent creates password (confirm twice) before locking; no default universal secret. Store only a salted slow password hash using standard platform cryptography (e.g. PBKDF2/Argon2 implementation with appropriate settings), restrict local access, never plaintext or web storage. Native top-level UI always shows a visible Exit button, outside the untrusted page, with accessible click target and no overlapping gameplay controls. Clicking Exit brings native password prompt with Cancel; correct password exits normally/unlocks as appropriate, wrong password keeps session locked with bounded retry delay, no lockout that risks permanently trapping parent. Also protect parent settings, change password and activity permissions with current password. Provide a documented safe local owner recovery process using normal OS controls. Never require secret keyboard combos. Explicitly preserve Ctrl+Alt+Delete, Task Manager/OS recovery and accessibility; no irreversible shell replacement, service, registry lockdown, credential interception or disabling secure desktop. Release restrictions automatically on wrapper exit, crash, signout or lost process; no global hooks or lingering processes when inactive. Do not launch an endless watchdog that relaunches after intentional exit or crash. Use normal window close interception/fullscreen and scoped, reversible handling of ordinary Alt+F4, minimization, Win key, Alt+Tab, taskbar focus and other accidental escape paths only to the extent reliably supported by OS. Test secondary monitors, focus loss, sleep/resume, dialogs, DPI, alt shortcuts and user recovery. This is accidental-exit protection, NOT a tamper-resistant kiosk or boundary against a determined user with OS access; explain that stronger restrictions would require separately configured Windows account/Assigned Access or supported equivalent. Do not compromise owner access.

WebView2 native policy: no browser chrome/address bar/history UI, devtools, context menu “search web” or external open, browser accelerator keys, arbitrary new windows, downloads, external URI schemes, shell launches or browser escape. Enforce exact trusted origins and normalized paths, frame/subframe navigation and resource/network requests (including redirects, deep links, percent-encoded paths, service worker/fetch, popups, drag/drop, links, downloads, permissions and web messages); use deny-by-default, test host/path spoofing and no generic prefix matching. Disable native bridge calls from unapproved origins; expose minimal validated messages only, never a password/exit privilege to web JavaScript. Do not rely on CSS hiding or client-side menu flags as security. Prefer offline local allowlisted resources; block external traffic including online speech if child mode offline. Keep an isolated WebView2 profile for child mode; no general browser account, cookies or stored TV credentials. Permit only explicitly vetted device capabilities and local assets. Decide whether updates need a separate native parent flow rather than exposing arbitrary browsing.

Default child-mode activity policy: vetted offline games/activities, encyclopedia, dictionary and Mouse Lab allowed; local same-device multiplayer allowed. Disable Internet multiplayer and Nearby/peer networking until explicitly approved; hide/deny Arcade Chat, TV (including media service credentials), unrestricted Comic Library remote browsing and arbitrary Windows file pickers. Permit only vetted local comics selected in parent mode, if feasible. Review Retro Vault, import/export features, image/file pickers, microphone/camera, URLs, online/shared mode, device permission prompts and any other routes that can expose unscreened content; don't break ordinary browser/Android features. Parent can enable specific activities and capabilities, with warnings for online/user-generated content. Enforce allowlist even on direct URL/deep link, iframe and game-internal navigation, not just menu. No external network or OS file selection in default locked mode. If an activity cannot be safely constrained, exclude it by default and report why. All existing games remain in regular Arcade.

Build using reproducible Windows CI and actual WebView2-capable Windows testing environment where possible; distinguish compile/test from real desktop behavior. Do not claim reliable lock/exit or physical Windows compatibility until exercised; if only Linux/headless CI available, deliver buildable project and Windows artifacts if verified, clearly identify untested real UI, provide short parent acceptance test, and mark wrapper incomplete pending needed verification. Keep no signing secrets in repo; do not sign without authorization.

## 9. Mouse compatibility and Mouse Lab

Audit EVERY enabled current catalog activity, recording activity ID, applicable inputs, tested device/viewport, pass/fail, exact repro and fix. Click = tap; mouse-down/hold = long press; drag/draw/aim via Pointer Events with capture/cancellation where appropriate; scroll and wheel where meaningful; keyboard remains functional; right-click and double-click only as useful actions; provide single-pointer/mouse alternatives for pinch, multi-touch and gesture-only actions. Do not synthesize duplicate click/touch events, lose dragging when pointer leaves target, block ordinary text selection/scroll, steal keyboard focus, or globally disable right-click needed for gameplay. Preserve Android touch and local multiplayer. For games intrinsically requiring simultaneous touch, design an explicit alternate keyboard/mouse control or record a justified limitation. Audit actual game interactions, not just page load, and both standard browsers and locked WebView2 mode.

Add Mouse Lab as a normal offline Arcade activity: large-to-small target clicking, pointer accuracy, moving targets, click-and-drag sorting, drawing/tracing, click-and-hold, double click, right click with explicit instruction, scroll wheel and simple simulated desktop/file-folder tasks (no real OS access). Gradual levels, adjustable sensitivity/difficulty, friendly feedback, no timers by default; persist local progress and offer repeat/reset. Use mouse and touch with pointer-specific alternatives; teach mouse without assuming touchscreen gestures are available. Test all exercises and accessibility, including small displays, mouse-only flow and no accidental exits.

## 10. Execution order, evidence and acceptance gates

A. Baseline: verify current source and CI, preserve existing saves and release integrity. Create implementation plan, work branch, data schema, inventory and coverage tracker. Establish baseline failing tests; fix only substantiated regressions or blockers.
B. Build shared encyclopedia/dictionary engine, search, accessible article view, integrated lookup, speech, local data and representative pilot. Test pilot actual content and revise editorial standards before scaling.
C. Author and verify real content in batches; maintain exact coverage/review counts and issue backlog. Commit batches and indices; expand across all domains rather than overfilling a single category. Do not stop with code generation scripts or a toy sample. Add verified visuals/quizzes as appropriate.
D. Register both activities, update manifest/package, test fresh install and offline update in real Chromium and Android-compatible bridge fixtures. Preserve prior versions and ordinary features. Publish verified incremental releases only when coherent; no premature broad completion.
E. Build native wrapper, parent password/settings, native security/recovery and allowed activity isolation. Validate on Windows with normal and adversarial interaction; build portable/reproducible artifacts and record runtime requirements. Add Mouse Lab and audit each game; keep touches working.
F. Run focused and broad regression suites, fix or document failures with baseline evidence, check build/deployment and artifact hashes, verify actual Library upload and final release. No weakened tests, fabricated results, or skipped scope disguised as completion.

Acceptance checks:
- Content: actual approved records present and searchable; independent count report with article/term/sense/question numbers, taxonomy and coverage, unresolved counts; meaningful source/license manifest; no broken links, duplicates or placeholders; tested age suitability and difficult/sensitive query cases.
- UX: search examples and typo corrections; no-result behavior, question graph, word definitions and inflection lookup, read aloud and Stop, local history/favorites/words, quizzes, responsive and keyboard/mouse/touch controls, Home and back restore.
- Offline: fresh verified snapshot, all core text/definitions and search after network cut, optional assets gracefully missing, update interrupted/corrupted recovery, existing game saves survive. No unauthorized external traffic or API calls.
- Windows: builds on target Windows, correct/wrong/forgotten password behavior, Exit always reachable, ordinary close/minimize/shortcut handling, OS emergency recovery still works, no lingering hooks, network/navigation/redirect/iframe/deep-link/popup/download/file/permission and native bridge tests, child allowlist enforced even with direct launch. Parent flow and normal mode not affected. Document known unavoidable Windows escape paths. Test failure recovery, multiple monitors, resize/DPI and sleep/resume where feasible.
- Mouse: full per-activity audit, real Playwright mouse and touch tests and actual Windows interactions when available, all Mouse Lab tasks; preserve gameplay and saves.
- Regression: catalog, shell, existing model/browser/multiplayer/nearby, Comic Library, Monster Forge, Tank Tactics, offline package. Run original failing baseline tests and inspect failures; compare source and evidence. Record exact commands, CI URLs, versions, pass/fail/skip and physical hardware limitations, not unsupported green claims.
